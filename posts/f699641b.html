漏洞简介

CVE-2026-64560：Linux 内核中 posix-cpu-timers 的非 leader exec 导致的 条件竞争 引发的 UAF 漏洞。

漏洞原理

该章节内部贴的源码对应内核版本 v6.17.9。
没有对 sighand 的访问加锁。

timer

timer 在 linux 中表示 “经过多少时间后触发”。而 CPU timer 表示消耗多少 CPU 时间。
CLOCK_PROCESS_CPUTIME_ID表示整个 thread group / process 消耗的 CPU 时间；
CLOCK_THREAD_CPUTIME_ID 表示单个线程消耗的 CPU 时间。

sighand

sighand 是 单个进程 task_struct 中的成员

一个多线程进程表示：

signal_struct 是整个 thread group 共享的状态。sighand_struct 是 signal handler / siglock。thread group leaderr 负责该 TGID 的特殊 task。
posix process cpu timer 是进程级资源，因此最终落在共享 signal_struct 上。
sighand 内部 存放成员 spinlock_t siglock，大量 signal / timer 相关数据修改，都需要拿 sighand->siglock。该锁一般由 lock_task_sighand 进行操作。

该函数会判断 sighand == NULL 如果为 NULL 则直接返回。
一般而言，p->sighand != NULL 表示 task 仍然存在，可以安全操作 sighand / timer queue
p->sighand == NULL 表示 task 正处于 sighand teardown / reaping 状态。

timerqueue

cpu timer 不能简单使用 hrtimer(high resolution timer)。
Linux 对 CPU timer 使用 timer queue，底层基于 rbtree。

进程与timer之间的关系：

timer_del() 调用 posix_cpu_timer_del。

过去 timer 中保存的是 task_struct 指针，导致出现 timer 访问 task_struct 时，该task是否已经发生改变。后来其成员被修改为了 struct pid 来规避这一问题。但是通过 pid 寻找 task （p = cpu_timer_task_rcu(timer)）也并非安全

Non-leader exec()

这里需要修正一个概念：

内核中的最小基本调度单元是线程，因此用户态的pid指的是 TGID 即线程组 id。TID 是内核调度的唯一标识(task_struct的pid)

因此在这里，假设有一个线程组(TGID=1000)，其内部存在线程A(pid = 1000, leader)，B(pid = 1001)。如果线程B调用 execve()，Linux 为了让 exec 后的进程继续拥有 TGID = 1000，会做 leader switch。内部涉及 de_thread->switch_leader。
因此更换 leader A 为 B。task A 会被 reaped。

漏洞原理

如果 de_thread 中旧 leader 被释放与 timer_del 中的 pid 查询同时发生，则可能导致 timer_del 拿到旧 leader。而该 leader 已经被释放，其会清空自己的 timers（per-thread timers） 并设置 sighand 为NULL。但是其不会对 timer list 做 dequeue 操作。而且 timer_del 中如果发现 sighand 为 NULL 后也会直接退出，不会进一步对 timer queue 释放。导致出现了 UAF。

漏洞修复

修复连接中的精髓应该是添加了一个 helper 函数：

将 pid task 的查找与 sighand 加锁通过 for 循环包括（即默认如果拿到 task 就必须能够成功加锁）这样的话面对上面的 race 会导致加锁失败继续循环，直到更换新的 leader 成功后才会成立。
然后就是一些小修小改，在 sighand 上下文添加了 smp_restore_release() 以及 smp_acquire__after_ctrl_dep() 来避免弱序内存操作的影响。
