bad epoll漏洞学习复现

发表于2026-08-03|更新于2026-08-27
|总字数:4.8k|阅读时长:23分钟|浏览量:

学习一下近期出现的 bad epoll 漏洞，该漏洞位于 fs/eventpoll.c，在 linux 内核以及 安卓内核中均存在该漏洞。

漏洞原理

漏洞位于 fs/eventpoll.c 的 ep_remove() 函数中。file 对象没有使用引用计数追踪或者加锁保护，导致可以通过构造一个 eventpoll fd 监视另一个 eventpoll fd，然后多线程竞争 close，导致 file 结构体的 UAF。
其存在问题源码位置，在 ep_remove 函数中，file 为传入 epitem 的 ffd.file 对象。对其继续调用 ep_remove_file() 函数。在该函数中会写入 file->f_ep 成员为 NULL。

而另一条路径上（或者应该说是上层调用链上）通过竞争抢占执行。__fput 函数调用 eventpoll_release 函数（开启 CONFIG_KCMP定义）会查看 file->f_ep 的内容。如果该 fast_check 检查到 f_ep 为空，则直接返回。

后续调用 file->f_op->release 即 eventpoll_fops->release，即 ep_eventpoll_release 函数。其继续向下调用至 ep_free，然后会直接 kfree epoll_target，在 file_free 中 kmem_cache_free file_target。

漏洞利用

由于该漏洞发现者声称该漏洞可以实现手机的 root 提权。因此会着重分析其漏洞利用思路并尝试进行迁移（其只提供了 x86 下 linux 内核的利用脚本）。
竞争时序如下：

该漏洞提交者还给出了 kernelctf 中的 exp ，这里我们也简单分析下其利用过程：

Stage1：环境初始化

该部分在 race_setup() 函数中：
创建共享的 timerfd 以及深度为 3 的 epoll chain。

  • 先创建一个 timerfd_wakeup 的 timer，然后通过 race_enqueue_waiters 向其绑定大量的 eventpoll fd。这样当 time up 时可以触发大量的 event poll 事件，如果这个time刚好在窗口内，可以有效延长时间的窗口，并导致中断发生。
  • 然后创建一个 深度为 3 的 epoll 链条 ep_race_fds[3]。该链条用于评判 race 是否成功（ep_race_oracle），如果 race 成功会导致 epoll 的深度变为1。
  • 然后简单测了一下 false sharing 的耗时，用于后续的 race half time window。

Stage2: 漏洞触发与 cross cache

该部分在 vuln_trigger_and_cross_cache() 函数中
实现了 close-vs-close race 并使用 pipe_buffer reclaim 该 slab page。

  • 首先申请了 pipe，并 fcntl 设置其 PIPE_SZ 为 0x100 * 0x1000，也就是 0x100 页。
  • 新创建 racer_thread，其会调用 race_close_thread 。在 CPU 0 上运行，会设置 absolute-time timer 设置为中断发生时间，然后忙等待(time_interrupt_fire - time_racer_launch_ahead)，直到要发生中断的时候 close，期待中断会发生在 close 甚至是 竞争窗口内部。进入 for loop，分为两种阶段，PHASE_STAT 遍历 [LO,HI]，筛选最容易发生 中断的 ahead idx；PHASE_EXEC 从 STAT 阶段给定的窗口中随机挑选一个值进行尝试。在 PHASE 开始前，会先设置了 timerfd_wakeup timerfd，令其在窗口内触发大量的 waitqueue 等待延长时间窗口。然后调用 close(ep_race_waiter)，同时会测量其调用 close 所使用的指令数，如果大于了一个阈值则认为发生了中断。如果是 PHASE_STAT 会将该 ahead_idx 加入记录；如果是 PHASE_EXEC 也会执行记录，并重新继续 PHASE_STAT。
  • 主进程会继续向下执行，绑定 CPU 1 运行。首先会打开/dev/null 填满 CPU partial_list。然后创建两个 epitem，ep_race_waiter，ep_race_target。ep_race_waiter 会 watch ep_race_target，CPU1 会释放 ep_race_target。然后再打开 /dev/null 填充 slab。然后启动 race 过程。不过主进程会进行 false sharing 延长时间窗口。
  • 检测是否race成功，如果 race 成功，目标的 refs 会被清空为0，尝试将 ep_race_oracle 添加到 ep_uaf_target 链表中，如果 refs 为空可以添加成功，如果 refs 不为空则会报错 MAX_NESTS。
  • 接下来就是 cross cache。将前面的 file 全部释放掉（除了与 ep_uaf_target 对应的 filefd）。然后 write(pipe_fd) 将释放的 file page 重新申请回来。通过一次受限的任意地址8字节读来判定是否 pipe_buffer reclaim 成功。
  • 后续就是任意8字节读写转化为任意地址读写

Stage3: ROP 提权

  • 新建 rop_pipe 用于写入 ROP 链
  • 通过任意地址读获取 rop_pipe 的 page 虚拟地址。
  • 填写page的ROP链
  • 调用 epoll_wait，该地址的 waiter->vfs_poll->fake fop 已经被修改，从而进入 rop_pipe page 链。

漏洞利用

x86_64

尝试修改以上 exp 的偏移适配到当前编译的内核上。
另外需要注意，以上漏洞复现部分的时间窗口实际上要比利用部分的时间窗口小。
因为漏洞利用部分的时间窗口应该位于 WRITE_ONCE 与 hlist_del_rcu 之间。而非 is_file_epoll()，或者更准确地说在 is_file_epoll 与 hlist_del_rcu 之间，因此相较于漏洞复现，该部分其实理论上成功率会更高一些。

要成功迁移以上exp到新编译内核。首先需要修改大量的内核偏移值。不过原作者提供 exp 的内部数据使用了 libxdk 以数据库的形式来保存各种偏移以及配置信息。只有少量的偏移配置硬编码在 exp 内。
因此，我们最好还是直接借助 libxdk 库来附加我们编译的内核到 kxdb 中。

在看 image_db 的时候发现可以下载 kxdb 的 kernelctf 的指定版本内核。用以模拟启动运行 exp，发现可以执行到 ROP，不过最后在执行 execve 前栈未平衡，简单修改了 RopUtils.cpp 中的 Ret2Usr 函数，可以成功执行并拿到 root shell （注意需要修改 bash 为 sh，因为模拟的文件系统中没有该项）。（当然，也尝试了 --vuln-trigger 选项，不出意料的没有触发）

不过还是要尝试迁移到新的内核上。
